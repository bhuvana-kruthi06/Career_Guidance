# Phase 3 — Backend hardening and matcher performance

## 1. Summary (5 lines)

Added a Bucket4j per-IP limit of 20 match calls per minute, with a bounded in-memory client bucket registry.  
Limited match bodies to 16 KB, skill sets to 100 entries, skill names to 120 characters, and topN to 25.  
Limited concurrent matcher subprocesses to four and return actionable 429 or 503 responses with retry guidance.  
Added request IDs, key-value request and matcher timing logs, dev/prod CORS profiles, and `GET /api/health`.  
Backend tests and frontend tests/build pass; performance baseline and manual full-stack verification remain unverified because local socket access was unavailable.

## 5. How to run and test

Run the API and frontend using the README Quick Start. The health/readiness check is available at `http://127.0.0.1:8091/api/health`. To run the benchmark against a known-running backend:

```powershell
python scripts/benchmark_api.py --base-url http://127.0.0.1:8091 --iterations 20
```

For production CORS, set `SPRING_PROFILES_ACTIVE=prod` and `CORS_ORIGINS` to the trusted browser origin(s). Tune request controls with `MATCH_RATE_LIMIT_CAPACITY`, `MATCH_MAX_BODY_BYTES`, and `MATCH_MAX_CONCURRENT`.

## 6. UNVERIFIED or incomplete

- Numeric p50/p95 baseline is not available; see the benchmark record for the exact attempts and limits.
- A full-stack live request to the newly built backend and manual browser verification could not be completed because local socket access failed.
- Rate buckets are in-memory and per backend instance. Multi-instance deployments would need a shared limiter store; that was not added.
- Health checks execute the Python skill-catalog operation on each request and may take a second or more.
- npm reported 3 dependency advisories (1 moderate, 2 critical); no dependency audit fixes were made.
